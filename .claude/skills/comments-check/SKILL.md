# 注释检查(comments-check)

## 用途

检查代码注释的质量,从三方面找问题:
1. 注释是否齐全(每个函数、重要核心代码都要有注释,大概「10 行里 3 行注释、7 行正文」)
2. 注释内容是否和代码真正做的事一致
3. 注释是否用「小白能看懂」的话写的

## 步骤

### 第 1 步:确定检查范围

- 先问用户「检查哪些文件 / 目录」。
- 用户说「随便 / 全部」时,检查本项目的主要源码:
  - 后端 `backend/app/`(Python:FastAPI 接口、LangChain RAG、SQLAlchemy 模型、认证)
  - 前端 `frontend/src/`(TypeScript:React 组件、Zustand 状态、axios 请求)
- 跳过:`.venv`、`node_modules`、`__pycache__`、`dist`、构建产物、锁文件、测试文件。

### 第 2 步:读代码,逐项检查

**① 注释是否齐全**

- 每个函数:顶部应有注释,说明「做什么、输入什么、输出什么」。
- 重要 / 核心逻辑(算法、复杂判断、容易踩坑的地方):应有行内注释解释「为什么这么做」。
- 比例参考:大约每 10 行里 3 行注释、7 行正文(粗略,不硬抠数字,关键是「重要代码都有解释」)。
- 找出:没注释的函数、大段「裸奔」无注释的核心代码。

**② 注释和代码是否匹配**

- 逐条读注释,对照它旁边的代码,看注释说的和代码做的是不是一回事。
- 找出:注释写错、过时(代码改了注释没改)、张冠李戴、会误导人的注释。

**③ 注释是否「小白视角」**

- 注释应该用大白话解释,而不是堆专业术语。
- 出现专业词(如「向量化」「RAG」「分块」「嵌入」「JWT」「ORM」「SSE」「闭包」「深拷贝」)时,要么用比喻 / 例子讲清楚,要么补一句通俗解释。
- 找出:让新手看不懂、太简略、纯英文术语无解释的注释。

### 第 3 步:出报告

按三个检查项分别列出问题:

**① 注释缺失**
- `文件:行号` — 哪个函数 / 代码段缺注释,缺什么(用途 / 参数 / 逻辑说明)

**② 注释与代码不符**
- `文件:行号` — 注释说了什么、代码实际做了什么、哪里对不上

**③ 注释不够小白**
- `文件:行号` — 哪句难懂、建议改成什么

最后总结:整体注释情况 + 最该先补的几处。

### 第 4 步:问是否要帮忙补注释

- 出完报告,问用户「要不要我直接帮忙补上 / 改正这些注释?」,用户同意后再动手改。

## 注意

- 只读代码、不改代码,除非用户明确要求补注释。
- 报告用大白话,用户是技术小白。
- 「3:7」是粗略比例,不是硬性考核;关键是「重要代码都有清晰解释」。
